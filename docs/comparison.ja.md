# convx と Qhull、CGAL、Rust のクレートの比較

この文書は記録であって、合否は判定しない。他のライブラリのほうが速かったり、使うメモリが少なかったりした組み合わせも、計測したものはすべて載せた。convx が CGAL と Qhull に十分追いついているかは、別の仕組みで判定している。[verification.md](verification.md) のパリティ計測がそれで、閾値を決めたデータセットを、結果を動かしうる変更のたびに測る。この比較のほうは、リリースのたびに一度、データとライブラリを増やして取る。

今回の計測日は 2026-10-19、convx のコミットは `3782373` で、ライブラリのコードは 0.1.1 として公開するものと同じである。数値はすべて [bench/summary.json](bench/summary.json) にある。

## 計測の方法

| | |
| --- | --- |
| マシン | Intel Core i5-13400F（性能コア 6、効率コア 4、16 スレッド）、メモリ 48 GB |
| OS | Windows 11 上の WSL2、Ubuntu 22.04.2、カーネル 5.15.133.1 |
| CPU の割り当て | すべてのプロセスをコア 2 に固定 |
| 負荷 | 1 分ごとに記録した CPU 使用率は、中央値 10%、最大 52% で、9 割の時間は 31% 以下だった。0.1.0 の比較（2026-10-14）と同じ CGAL と Qhull の時間は、そのときと 1% 以内で一致した |
| Rust | 1.99.0、release プロファイル |
| C++ | g++ 11.4.0、`-O3 -DNDEBUG`。GMP 6.2.1 |

| ライブラリ | バージョン | 演算 |
| --- | --- | --- |
| convx | `3782373` | `f64` の入力から、すべての述語の符号を厳密に決める |
| CGAL | 5.4 | `f64` に対する厳密な述語（D = 2、3 は `Epick`、それより上は `Epick_d`） |
| Qhull | 2020.2 | 浮動小数点。許容誤差の範囲にあるファセットは統合する |
| `spade` | 2.15.1 | 厳密な述語 |
| `delaunator` | 1.1.0 | ロバストな向きの判定。等しい点は統合しない |
| `delaunay` | 0.8.2 | 厳密な述語 |
| `parry3d-f64` | 0.31.1 | 浮動小数点 |
| `geo` | 0.33.1 | ロバストな向きの判定 |

手順は [benches/compare/README.md](../benches/compare/README.md)、計測した組み合わせの一覧は [benches/compare/rows.txt](../benches/compare/rows.txt) にまとめてある。

- **時間**：出力を作るのにかかった時間で、各ライブラリが自分のプロセスの中で測る。ファイルの読み込みは含めていない。同じデータの計測では、ライブラリを入れ替えながらラウンドを回した。convx の最初の構築が 1.5 秒未満のデータは 1 ラウンドに 3 回ずつ 5 ラウンド、1.5 秒以上のデータは 1 回ずつ 3 ラウンドである。Qhull だけは 1 プロセスで 1 回構築し、Qhull 自身が出力する「CPU seconds to compute hull (after input)」を時間とした。表の値は中央値で、括弧の中は convx の中央値との比である。1 より大きければ convx より遅く、1 より小さければ convx より速い。
- **ピークメモリ**：ファイルを読んで 1 回だけ構築するプロセスの最大常駐セットサイズで、3 回測った中央値を載せた。値は、GNU time がカーネルの `ru_maxrss` から読んだものである。プロセス全体の量なので、ファイルから読んだ点の分は、どのライブラリの値にも入っている。
- **メモリ使用量の推移**：同じく 1 回だけ構築するプロセスの常駐セットサイズを、2 ms ごとに読んだもの。

計測する区間で作る出力は、ライブラリごとに違う。何を作るかの違いも、比べる対象の一部である。

- **convx**：`build()` が返すものすべて。凸包なら、頂点と、頂点の一覧と隣接を持つファセットに加えて、入力のすべての点が頂点、境界上の点、内部点、重複点のどれになったか。三角形分割なら、単体と各面の隣接。
- **CGAL**：凸包はその表面、三角形分割はセルと隣接を平らな配列に書き出したもの。CGAL が持っている情報の範囲で、convx と同じ出力にそろえた。
- **Qhull**：ファセットを頂点の番号で表し、ファイルに書き出したもの。
- **Rust のクレート**：各クレートが自分で持つデータ構造。アダプタは `benches/compare/rust/` にある。

## データ

| 区分 | 内容 | ファイル |
| --- | --- | --- |
| rbox | Qhull の生成器（シード 1）による立方体内の一様分布、球面上の点、回転した整数格子、1e-8 以内に近接点を持つ点 | D = 2〜8、10^3〜10^6 点 |
| PBBS | Problem Based Benchmark Suite の分布を同じ式で生成したもの：球内の一様分布、Kuzmin 分布（D = 2）、Plummer 分布（D = 3） | 10^5〜10^7 点 |
| スキャン | Stanford 3D Scanning Repository の Bunny、Dragon、Happy Buddha、Armadillo | 35,947〜543,652 点 |

スキャンデータの権利は Stanford Computer Graphics Laboratory（http://graphics.stanford.edu/data/3Dscanrep/）にある。計測する人が各自ダウンロードすることとし、このリポジトリでは再配布しない。

## ライブラリごとの違い

- **対応する次元**：convx は、凸包も三角形分割も次元を選ばない（ここでは D = 2〜8 を測った）。CGAL と Qhull も同じである。`spade`、`delaunator`、`geo` は D = 2 だけ、`parry3d-f64` は D = 3 だけ、`delaunay` は D = 2〜5 を扱う。
- **厳密さ**：convx、CGAL、`spade` は符号を厳密に決めるので、同じ点からは同じ頂点とファセット、同じ単体と隣接が出てくる。Qhull と `parry3d-f64` は浮動小数点で判定するので、頂点やファセット、サイトが少なく出ることがある。その差は、下の「出力の数が異なるケース」の表にまとめた。
- **論理ファセット**：convx のファセットは、厳密に同じ超平面に載る単体をひとまとめにしたもので、格子の立方体なら 6 枚になる。CGAL は D = 3 で三角形を 12 枚返す。D = 4 の格子では、凸包の頂点が 16 個なのに対し、CGAL は頂点 5,904 個を返す。Qhull は許容誤差の範囲でファセットをまとめるので、厳密に同じ平面にあるものだけでなく、ほぼ同じ平面にあるものも一つになる。
- **同一球面上のサイト**：同じ球面に載るサイトのグループを、convx と CGAL は単体に分ける。Qhull は、グループを一つの領域のまま出す。D = 2 の格子なら、Qhull は正方形 9,801 個、convx と CGAL は三角形 19,602 個になる。
- **入力点の分類**：入力の点を一つずつ、頂点、境界上の点、内部点、重複点のどれかに分け、重複点にはどの点と同じかまで付けるのは convx だけである。この分類は convx の計測区間に入っているが、ほかのライブラリはそもそも計算しない。
- **サイトの除外**：Qhull の Delaunay 三角形分割は、ほかのサイトに近すぎると見たサイトを出力に入れない。Kuzmin 分布の 10^5 サイトのうち、出力に残るのは 57,938 個である。

### 他のライブラリが速いケース

- **凸包**：42 件のうち 16 件で、convx 以外のライブラリが最も速い。Qhull のほうが速いのは、`cube` D3 の 10^6 点（0.89）、`sphere` D3 の 10^4 点と 10^5 点（0.94 と 0.99）、`sphere` D5（0.98）、D = 3 と 4 の格子（0.98 と 0.41）、D3 の Plummer 分布（0.85 と 0.64）、Dragon と Buddha のスキャン（0.94 と 0.82）である。CGAL は D = 2 の格子（0.40）と、Kuzmin 分布の 10^5 点と 10^6 点（0.51 と 0.39）で速いが、10^7 点では遅い（6.48）。D2 の球内の一様分布の 10^5 点では同等（1.00）である。`geo` は `cube` D2 の 10^6 点（0.98）と Kuzmin 分布（0.62 と 0.62）で、`parry3d-f64` は `cube` D3（0.85 と 0.97）と Plummer 分布（0.45 と 0.82）で速い。
- **Delaunay**：38 件のうち 21 件で、convx 以外のライブラリが最も速い。CGAL のほうが速いのは 18 件である。convx に対する比は、D = 2 の格子で 0.72、D = 3〜5 の `cube`、`near`、球内の一様分布、Plummer 分布で 0.87〜0.98、四つのスキャンで 0.81〜0.88 である。Qhull は D4 と D5 の 10^3 点のデータで速い（0.91 と 0.90）。`spade` は Kuzmin 分布の 10^5 サイト（0.90）で、`delaunator` は `cube` D2 の 10^5 点（0.78）と Kuzmin 分布の 10^5 サイト（0.99）で速い。これらが入る D = 2 のほかのデータでは、convx のほうが速い。
- **メモリ**：凸包では、42 件のうち 36 件で Qhull のメモリ使用量が最も少ない。D = 2 の三角形分割では、`spade` と `delaunator` のメモリ使用量は convx の 94〜100% である。Kuzmin 分布の 10^6 と 10^7 サイトでは、Qhull の三角形分割のメモリ使用量は convx の 57% と 33% だが、大半のサイトを出力から除いている。

### convx が速いケース

- **凸包**：42 件のうち 26 件で convx が最も速い。特に差が大きいのは、D ≥ 4 での CGAL との比較（`cube` で 2.7〜22 倍）、D2 の球面上の点での Qhull との比較（9.4〜19 倍）、D3 の球面上の点での `parry3d-f64` との比較（3.0 倍と 29 倍）である。
- **Delaunay**：convx が CGAL より速いのは、格子を除く D = 2 のすべてのデータ（1.15〜1.81）、D3 と D4 の球面上の点（1.13〜2.84）、D = 3 と 4 の格子（1.07 と 1.54）、`cube` D5 の 10^3 点（1.05）である。`spade` には 4 件のうち 3 件で（1.06〜1.20）、`delaunator` には 2 件で（1.15 と 1.47）速い。Qhull と比べると、D4 と D5 の 10^3 点の 2 件を除くすべての Delaunay の計測で convx が速い。
- **メモリ**：convx の三角形分割のメモリ使用量は、格子（76〜87%）を除けば CGAL のピークの 40〜62% である。D3 の 10^4 点以上のデータでは、格子（87%）を除けば Qhull の 25〜52% にとどまる。

## 比較しなかったもの

- **D = 5 の `delaunay` クレート**：0.1.0 の比較で、1,000 点を 3 回構築するプロセスが 81 分たっても終わらなかったため、このデータは `delaunay` クレートを除いて計測している。D = 2〜4 では、1,000 点の構築にそれぞれ 0.46 秒、3.7 秒、136 秒かかった。
- **比較しなかったクレート**：網羅ではなく主なものに絞ったため、`qhull`（Qhull へのバインディング。Qhull 本体を比較に含めている）、`chull`、`tritet`、`startin`、`voronoice`、`voronator` は計測していない。
- **Voronoi 図**：比較したライブラリの中に、convx と同じ出力を作るものはない。convx の Voronoi 図は、Delaunay 三角形分割を作ってから頂点ごとに線形方程式を解いて求める。
- **マルチスレッド**：すべてのライブラリを 1 コアで実行した。CGAL には並列処理の三角形分割があるが、convx の構築は逐次処理である。

## 再計測の手順

```sh
bash benches/compare/setup.sh <commit>
for tier in rbox pbbs scans; do bash benches/compare/data/make.sh $tier; done
cd ~/convx-compare
python3 <repo>/benches/compare/runner.py <repo>/benches/compare/rows.txt results.jsonl
python3 <repo>/benches/compare/publish.py results.jsonl <repo>/docs/bench <meta.json>
```

`publish.py` が `summary.json` と図を出力する。約 950 MB のデータは、計測が終わったら削除する。
