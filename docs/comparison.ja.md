# convx と Qhull、CGAL、Rust のクレートの比較

この文書はベンチマークの記録であり、合否の判定はしない。計測した組み合わせはすべて載せており、他のライブラリのほうが速いケースやメモリ使用量が少ないケースも除いていない。CGAL と Qhull に対して convx が十分に速いかどうかの判定は、別に [verification.md](verification.md) のパリティ計測で行っている。パリティ計測は閾値つきの決まったデータセットで、結果に影響しうる変更のたびに実行する。この比較はリリースごとに一度、より多くのデータとライブラリで実行する。

計測は 2026-10-18 に、convx のコミット `536c11c` で行った。ライブラリのコードは 0.1.1 で公開するものと同じである。すべての数値は [bench/summary.json](bench/summary.json) に収めている。

## 計測の方法

| | |
| --- | --- |
| マシン | Intel Core i5-13400F（性能コア 6、効率コア 4、16 スレッド）、メモリ 48 GB |
| OS | Windows 11 上の WSL2、Ubuntu 22.04.2、カーネル 5.15.133.1 |
| CPU の割り当て | すべてのプロセスをコア 2 に固定 |
| 負荷 | 計測中の CPU 使用率を 1 分ごとに記録した。中央値は 23% で、9 割の時間は 40% 以下だった。0.1.0 の比較（2026-10-14）から変わっていない CGAL と Qhull も、そのときより 6〜10% 遅く出た。表の時間はマシンが遅い状態でのものであり、比べるべきは、同じ行のライブラリを交互に回して取った比である |
| Rust | 1.99.0、release プロファイル |
| C++ | g++ 11.4.0、`-O3 -DNDEBUG`。GMP 6.2.1 |

| ライブラリ | バージョン | 演算 |
| --- | --- | --- |
| convx | `536c11c` | `f64` の入力から、すべての述語の符号を厳密に決める |
| CGAL | 5.4 | `f64` に対する厳密な述語（D = 2、3 は `Epick`、それより上は `Epick_d`） |
| Qhull | 2020.2 | 浮動小数点。許容誤差の範囲にあるファセットは統合する |
| `spade` | 2.15.1 | 厳密な述語 |
| `delaunator` | 1.1.0 | ロバストな向きの判定。等しい点は統合しない |
| `delaunay` | 0.8.2 | 厳密な述語 |
| `parry3d-f64` | 0.31.1 | 浮動小数点 |
| `geo` | 0.33.1 | ロバストな向きの判定 |

計測手順は [benches/compare/README.md](../benches/compare/README.md)、計測した組み合わせの一覧は [benches/compare/rows.txt](../benches/compare/rows.txt) にある。

- **時間**：各ライブラリが出力を構築するのにかかった時間を、そのライブラリのプロセスの中で測った。ファイルの読み込みは含まない。同じデータに対する各ライブラリの計測は、ラウンドごとに交互に実行した。convx の最初の構築が 1.5 秒未満なら 3 回ずつ 5 ラウンド、それ以外は 1 回ずつ 3 ラウンド実行した。Qhull はプロセスごとに 1 回だけ構築し、Qhull 自身が出力する「CPU seconds to compute hull (after input)」を記録した。表には中央値と、括弧内に convx の中央値に対する比を載せている。比が 1 より大きければそのライブラリは convx より遅く、1 より小さければ速い。
- **ピークメモリ**：ファイルを読んで 1 回だけ構築するプロセスの最大常駐セットサイズ（3 回計測した中央値）である。値はカーネルの `ru_maxrss` を GNU time で取得している。プロセス全体の値なので、入力の点を読み込んだ分のメモリはどのライブラリにも同じように含まれる。
- **メモリ使用量の推移**：同じように 1 回構築するプロセスの常駐セットサイズを、2 ms 間隔でサンプリングした。

計測区間で各ライブラリが作る出力は同じではなく、その違いも比較の一部になる。

- **convx**：`build()` が返すもの。凸包では、頂点、頂点の一覧と隣接ファセットを持つファセット、入力の全点の分類（頂点、境界上の点、内部点、重複点）。三角形分割では、隣接関係つきの単体。
- **CGAL**：凸包の表面と、三角形分割のセルとその隣接を 1 次元の配列に書き出したもの。CGAL が持つ情報の範囲で convx と同じ出力にそろえている。
- **Qhull**：頂点で表したファセットをファイルに書き出したもの。
- **Rust のクレート**：それぞれのクレート自身のデータ構造（アダプタは `benches/compare/rust/` にある）。

## データ

| 区分 | 内容 | ファイル |
| --- | --- | --- |
| rbox | Qhull の生成器（シード 1）による立方体内の一様分布、球面上の点、回転した整数格子、1e-8 以内に近接点を持つ点 | D = 2〜8、10^3〜10^6 点 |
| PBBS | Problem Based Benchmark Suite の分布を同じ式で生成したもの：球内の一様分布、Kuzmin 分布（D = 2）、Plummer 分布（D = 3） | 10^5〜10^7 点 |
| スキャン | Stanford 3D Scanning Repository の Bunny、Dragon、Happy Buddha、Armadillo | 35,947〜543,652 点 |

スキャンデータの権利は Stanford Computer Graphics Laboratory（http://graphics.stanford.edu/data/3Dscanrep/）にある。計測する人が各自ダウンロードすることとし、このリポジトリでは再配布しない。

## ライブラリごとの違い

- **対応する次元**：convx は任意の次元の凸包と三角形分割を作る（ここでは D = 2〜8 を計測した）。CGAL と Qhull も同様である。`spade`、`delaunator`、`geo` は D = 2 のみ、`parry3d-f64` は D = 3 のみ、`delaunay` は D = 2〜5 に対応する。
- **厳密さ**：convx、CGAL、`spade` は厳密な符号で判定するので、同じ点に対して同じ頂点とファセット、同じ単体と隣接関係を返す。Qhull と `parry3d-f64` は浮動小数点で判定するため、出力される頂点、ファセット、サイトの数が少なくなることがある（後述の出力の数を参照）。
- **論理ファセット**：convx のファセットは、厳密に同じ超平面上にある単体をまとめたものである。格子の立方体なら 6 枚になる。CGAL は D = 3 では三角形 12 枚を返す。D = 4 の格子では、凸包の頂点は 16 個だが、CGAL は頂点を 5,904 個返す。Qhull は許容誤差の範囲にあるファセットを統合するので、厳密に同一平面上のファセットに加えて、ほぼ同一平面上のファセットもまとめられる。
- **同一球面上のサイト**：convx と CGAL は、同じ球面上にあるサイトのグループを単体に分割する。Qhull はグループを一つの領域として出力する。たとえば D = 2 の格子では、Qhull は正方形を 9,801 個、convx と CGAL は三角形を 19,602 個出力する。
- **入力点の分類**：convx は、入力の各点を頂点、境界上の点、内部点、重複点のいずれかに分類し、重複点にはどの点の重複かも出力する。この分類は convx の計測区間に含まれるが、他のライブラリはこれを計算しない。
- **サイトの除外**：Qhull の Delaunay 三角形分割は、他のサイトに近すぎると判断したサイトを出力から除く。Kuzmin 分布の 10^5 サイトでは、出力に残るのは 57,938 個である。

### 他のライブラリが速いケース

- **凸包**：42 件のうち 16 件で、convx 以外のライブラリが最も速い。Qhull のほうが速いのは、`cube` D3 の 10^6 点（0.95）、`sphere` D3（0.95、0.99、0.97）、`sphere` D5（0.97）、D = 3 と 4 の格子（0.91 と 0.43）、D3 の Plummer 分布（0.81 と 0.64）、Dragon と Buddha のスキャン（0.91 と 0.87）である。CGAL は D = 2 の格子（0.39）と、Kuzmin 分布の 10^5 点と 10^6 点（0.51 と 0.42）で速いが、10^7 点では遅い（6.92）。`geo` は `cube` D2 の 10^6 点（0.86）と Kuzmin 分布（0.63 と 0.60）で、`parry3d-f64` は `cube` D3 の 10^5 点（0.87）と Plummer 分布（0.53 と 0.85）で速い。
- **Delaunay**：38 件のうち 21 件で、convx 以外のライブラリが最も速い。CGAL のほうが速いのは 19 件で、D = 2 の格子（0.71）を除いてすべて D ≥ 3 である。convx に対する比は、D3 の `cube`、`near`、球内の一様分布、Plummer 分布で 0.84〜0.98、`cube` D4 と D5 で 0.93〜0.95、D = 3 の格子で 0.99、四つのスキャンで 0.82〜0.87 である。Qhull は D4 の 10^3 点のデータで速い（0.91）。`spade` は Kuzmin 分布の 10^5 サイト（0.92）で、`delaunator` は `cube` D2 の 10^5 点（0.79）で速い。これらが入る D = 2 のほかのデータでは、convx のほうが速い。
- **メモリ**：凸包では、42 件のうち 36 件で Qhull のメモリ使用量が最も少ない。D = 2 の三角形分割では、`spade` と `delaunator` のメモリ使用量は convx の 94〜100% である。Kuzmin 分布の 10^6 と 10^7 サイトでは、Qhull の三角形分割のメモリ使用量は convx の 57% と 33% だが、大半のサイトを出力から除いている。

### convx が速いケース

- **凸包**：42 件のうち 26 件で convx が最も速い。特に差が大きいのは、D ≥ 4 での CGAL との比較（`cube` で 2.5〜21 倍）、D2 の球面上の点での Qhull との比較（9.5〜20 倍）、D3 の球面上の点での `parry3d-f64` との比較（2.9 倍と 33 倍）である。
- **Delaunay**：convx が CGAL より速いのは、格子を除く D = 2 のすべてのデータ（1.18〜1.80）、D3 と D4 の球面上の点（1.11〜2.82）、D = 4 の格子（1.59）、`cube` D5 の 10^3 点（1.07）である。`spade` と `delaunator` に対しては、それぞれ 4 件のうち 3 件で速い（1.06〜1.14 と 1.04〜1.48）。Qhull と比べると、D4 の 10^3 点の 1 件を除くすべての Delaunay の計測で convx が速い。
- **メモリ**：convx の三角形分割のメモリ使用量は、格子（84〜87%）を除けば CGAL のピークの 40〜63% である。D3 の 10^4 点以上のデータでは、格子（87%）を除けば Qhull の 25〜52% にとどまる。

## 比較しなかったもの

- **D = 5 の `delaunay` クレート**：0.1.0 の比較で、1,000 点を 3 回構築するプロセスが 81 分たっても終わらなかったため、このデータは `delaunay` クレートを除いて計測している。D = 2〜4 では、1,000 点の構築にそれぞれ 0.49 秒、3.9 秒、149 秒かかった。
- **比較しなかったクレート**：網羅ではなく主なものに絞ったため、`qhull`（Qhull へのバインディング。Qhull 本体を比較に含めている）、`chull`、`tritet`、`startin`、`voronoice`、`voronator` は計測していない。
- **Voronoi 図**：比較したライブラリの中に、convx と同じ出力を作るものはない。convx の Voronoi 図は、Delaunay 三角形分割を作ってから頂点ごとに線形方程式を解いて求める。
- **マルチスレッド**：すべてのライブラリを 1 コアで実行した。CGAL には並列処理の三角形分割があるが、convx の構築は逐次処理である。

## 再計測の手順

```sh
bash benches/compare/setup.sh <commit>
for tier in rbox pbbs scans; do bash benches/compare/data/make.sh $tier; done
cd ~/convx-compare
python3 <repo>/benches/compare/runner.py <repo>/benches/compare/rows.txt results.jsonl
python3 <repo>/benches/compare/publish.py results.jsonl <repo>/docs/bench <meta.json>
```

`publish.py` が `summary.json` と図を出力する。約 950 MB のデータは、計測が終わったら削除する。
